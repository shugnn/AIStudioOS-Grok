## 1. 讨论起因

1. 工程侧已有控制平面、L1、浸泡、监督、急停等证据，但业务推进时出现 **对话侧（轨道执行者）直接编写 `ingest_live_free.py` / `run_live_pipeline.py` 再交宿主运行** 的路径。  
2. 创始人指出：这与创立初衷不符——产品应是 **有头有手的工作团队**，在目标、资源、授权下 **自主** 寻找/配置工具并完成复杂业务，而不是单兵玩具题或「外人写好脚本、系统只负责跑」。  
3. 创始人进一步要求：产品必须是 **独立工作系统**，不依赖任何特定大模型；完工后 **人类可直接启动与操控**；Grok 及其它 AI 均退居 **可插拔部件**（可为指挥中枢或工人），可被产品插拔、调用、替换。  
4. 创始人确认：在「是否已具备自我迭代」上，当前答案为 **否**；但 **可插拔、自己拆活并实现、独立验收驱动、自我迭代** 必须写入 **产品定位**（目标态），未实现不得宣传为已具备。

## 2. 决策清单（必须同步）

| ID | 决策 | 含义 |
|----|------|------|
| D-P1 | 初衷有效 | 人类给目标/资源/授权 → 多角色规划·执行·验证·恢复·迭代 → 证据验收 |
| D-P2 | 模型无关 | 不绑定 Grok、ChatGPT 或任何一家模型；产品是 OS/框架 |
| D-P3 | 人类直操 | 完工验收要求：仅本机文档流程可启动、授权、急停、看状态；不依赖某聊天 AI 在线代写 |
| D-P4 | AI 可插拔 | LLM 只能是中枢 / 工人 / 工具实现，可替换；不是产品本体 |
| D-P5 | 定位含四项能力 | **可插拔** · **自己拆活并实现改动** · **独立验收驱动** · **自我迭代** |
| D-P6 | 诚实状态 | 四项中：拆活实现与自我迭代当前 **未具备**；可插拔仅占位；验收驱动仅部分 |
| D-P7 | 脚手架政策 | 对话侧手写业务流水线 = scaffold/baseline，**不计** 自治/自我迭代 PASS |
| D-P8 | 禁止路径 | 用「轨道员聊天写代码 + push + 宿主只跑」冒充工作室自治完成 |
| D-P9 | 双轨 | 不改对方仓库；ChatGPT 轨应理解并在本轨叙事上对齐，避免再宣传「脚本工人=团队」 |
